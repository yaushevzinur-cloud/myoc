# MyOS: паспорт проекта и правила разработки

Этот файл действует для всего репозитория. MyOS — персональная Life OS владельца. Владелец не обязан быть программистом и ставит задачи обычным языком. Исполнитель сам изучает относящийся к задаче существующий код и данные, выбирает наиболее безопасную совместимую реализацию, вносит изменения непосредственно в репозиторий и проверяет результат. Нельзя перекладывать на владельца ручное редактирование файлов, если это можно сделать самостоятельно.

## Неприкосновенные правила

1. Сохранять весь существующий работающий функционал и все пользовательские данные. Перед изменением проследить существующие пути чтения, записи, импорта, синхронизации и отображения затронутых данных.
2. Никогда не очищать существующие данные ради миграции, исправления или перехода на новую версию. Нельзя без прямого указания менять ключ хранилища так, чтобы старые данные стали недоступны.
3. MyOS используется одновременно с iPhone, Android, планшета и ПК. Корректная синхронизация между устройствами — критическое требование, а не дополнительная возможность.
4. Supabase — облачное хранилище и транспорт синхронизации; `localStorage` — локальное хранилище и основа offline-работы. Приложение должно оставаться полезным без сети и синхронизироваться после её восстановления.
5. Любое изменение структуры данных выполнять только через безопасную, идемпотентную и обратносуместимую миграцию: дополнять отсутствующие поля, сохранять неизвестные поля и старые записи, поддерживать чтение прежнего формата. До миграции определить инварианты и путь отката без потери данных.
6. Никогда не заменять целиком уникальные данные одного устройства состоянием другого. Для коллекций нужны стабильные уникальные ID, слияние по сущностям и явная семантика изменений/удалений; для конфликтов — метаданные на уровне записи или поля. Устаревшее устройство не должно перезаписывать более свежие данные.
7. Не изменять, не печатать, не цитировать, не коммитить заново и не раскрывать содержимое `config.js`, ключи, токены и секреты. Клиентская конфигурация Supabase уже подключается через `window.MYOS_CONFIG`; серверные секреты должны поступать только из переменных окружения.
8. Не трогать отдельный проект **Game Room**: не читать, не редактировать, не переносить и не включать его файлы в изменения MyOS. Если он появится рядом с MyOS или внутри рабочей области, считать его отдельным репозиторием/продуктом вне области задачи.
9. Не удалять существующие модули, экраны, данные или возможности без прямого указания владельца. Заглушки и незавершённые ветки интерфейса также не удалять как «неиспользуемые» без проверки намерения.
10. Не создавать ZIP или иной пакет для ручной установки, если изменение можно внести непосредственно в репозиторий.
11. После существенного релиза согласованно обновлять отображаемую версию MyOS во всех местах интерфейса и cache-busting ссылках. Не повышать версию за документацию или мелкое внутреннее изменение.
12. Перед завершением каждой задачи проверять синтаксис изменённых JS-файлов и основные затронутые пользовательские сценарии. Для данных отдельно проверять обновление существующего состояния, offline-сохранение, повторную загрузку и слияние с облаком.
13. Делать минимальный целевой diff. Не проводить попутный рефакторинг и не переписывать работающую архитектуру без необходимости задачи.

## Фактическая архитектура на момент создания паспорта

### Основное приложение

- Рабочая версия — мобильное web/PWA-приложение без сборщика: `index.html` подключает `style.css`, затем `config.js` и единый `app.js`. Интерфейс русскоязычный, адаптивный и ориентирован на телефон, но должен работать на планшете и ПК.
- `app.js` — монолитный vanilla JavaScript: единый объект `state`, шаблоны экранов через HTML-строки, прямые DOM-обработчики и центральный маршрутизатор `render(page)`. Нижняя навигация открывает «Сегодня», «План», добавление, «Прогресс» и «Я»; вложенные экраны вызываются из этих разделов.
- `style.css` — общая тёмная дизайн-система и последовательно добавленные стили версий/модулей. При изменениях сохранять mobile-first поведение, safe areas, доступные размеры элементов и существующие классы.
- `manifest.webmanifest` задаёт standalone PWA. `sw.js` сейчас активирует новую версию, удаляет caches и не перехватывает fetch содержательно; полноценного app-shell cache в нём нет.
- Отображаемая web-версия сейчас — `V0.24.0` в `index.html` и шаблонах `app.js`; query-параметры CSS/JS используются как cache busters.

### Данные и синхронизация

- Главный локальный state хранится одним JSON под историческим ключом `localStorage` **`myos03`**. Этот ключ и совместимость его содержимого сохранять.
- При старте отсутствующие верхнеуровневые структуры дополняются значениями по умолчанию. В коде есть встроенные миграции/инициализаторы для планировщика, целей, языков, профессионального развития, Work и питания. Новые миграции должны следовать add-only/idempotent подходу и не заменять пользовательские массивы демонстрационными значениями.
- `save()` записывает state локально сразу и планирует облачную синхронизацию. Поэтому локальная запись должна успешно завершаться независимо от наличия сети или Supabase.
- Supabase вызывается напрямую через REST endpoint таблицы `myos_data`; строка выбирается по `user_key`, полезная нагрузка находится в поле `data`, а `updated_at` используется для optimistic compare-and-swap при записи.
- Текущий код уже содержит `_sync.version`, `_sync.clocks`, `_updatedAt`, стабильные `_syncId` для legacy-элементов, рекурсивное слияние объектов/массивов и повтор записи при конфликте. Это важный существующий фундамент, но его нельзя считать окончательным выполнением требований V0.24 без сценарных тестов разошедшихся устройств, удалений, одинаковых legacy-записей и устаревших клиентов.
- Повторная синхронизация уже инициируется после локального сохранения, при старте, событиях `online`, `focus` и возврате `visibilitychange` в visible; `offline` отражается в статусе интерфейса.
- Удаления и идентичность элементов особенно чувствительны: перед изменением merge-алгоритма проверить, как конкретная сущность получает `id`/`_syncId`, как фиксируется удаление и не может ли удалённая запись самопроизвольно вернуться.

### Существующие функциональные области

- **Сегодня:** сводка дня, фокус, ритм дня, краткие метрики и переключатель режима «Вахта/Дом».
- **Планировщик/задачи:** горизонты день/неделя/месяц/год, календарная дата, статусы, приоритет, длительность, области жизни, переносы, просрочка, архив и связи с целями/профессиональным развитием.
- **Цели:** целевое значение и прогресс, срок, статус, область жизни и связанные задачи.
- **Чтение:** библиотека, текущая/общая страница, дневная цель и история чтения по датам.
- **Питание/КБЖУ:** дни и приёмы пищи, дневные цели, итоги КБЖУ, ручное добавление, удаление, выбор даты, импорт блока `MYOS:` и отдельный AI-поток фото/описания с обязательным экраном проверки перед сохранением.
- **Языки:** казахский, английский и китайский; дневные минуты/цели, история, серии и заметки/активности.
- **Профессиональное развитие:** треки, элементы обучения, база знаний и связь с задачами планировщика.
- **Work:** договоры, проекты/скважины, склад и упаковки, этапы работ, резерв, подтверждённая отгрузка и история складских движений. Операции списания нельзя делать повторно или терять при синхронизации.
- **Прогресс и аналитика:** выполнение задач по периодам и областям, тренды, сравнение с предыдущим периодом и краткие выводы.
- **Тренировки, привычки, дневник и утренние/вечерние ритуалы:** являются обязательными направлениями MyOS; часть пока представлена в сводках/навигации или заглушках и должна развиваться без удаления существующих точек входа.

### Серверный и альтернативный код

- `api/analyze-food.js` — serverless HTTP endpoint для AI-оценки питания. Он принимает фото/описание, вызывает OpenAI Responses API с серверным `OPENAI_API_KEY` и возвращает структурированный JSON. Никогда не переносить этот ключ или AI-вызов в клиент; ошибки AI не должны ломать ручной ввод или импорт.
- `App.js`, `app.json` и Expo-зависимости в `package.json` образуют отдельный ранний React Native/Expo прототип одного экрана. Основной функциональный продукт при этом находится в корневом web/PWA-коде. Не смешивать две реализации и не считать прототип источником истины без прямой задачи на Expo.
- `MyOS-Web-V0.11.2-goals-ui-polish/` — сохранённый legacy-снимок web-версии с собственными HTML/CSS/JS/manifest/service worker и `config.js`. Это не активная точка входа. Не синхронизировать его автоматически с текущей версией, не удалять и не использовать его старую whole-state cloud sync как образец.
- Автоматизированного test suite, линтера и шага web-сборки сейчас нет. `package.json` относится к Expo-прототипу; основной web-клиент запускается как статические файлы, а `api/` рассчитан на serverless-хостинг (текущий README упоминает Vercel).

## Основные направления MyOS

Развитие продукта должно сохранять общую Life OS, а не превращать приложение в один узкий трек:

1. Сегодня.
2. Планировщик и задачи.
3. Цели.
4. Чтение.
5. Питание и КБЖУ.
6. Тренировки.
7. Привычки.
8. Казахский, английский и китайский языки.
9. Профессиональное развитие.
10. Work.
11. Дневник, утренние и вечерние ритуалы.
12. Прогресс и аналитика.

## Очередь ближайшей разработки

Очередь фиксирует цели следующих релизов, но **не является разрешением начинать их в рамках другой задачи**.

### V0.24 — Multi-device Sync

- Безопасно объединить уже разошедшиеся локальные данные iPhone, Android и других устройств.
- Устранить whole-state last-write-wins и сохранить все уникальные записи.
- Синхронизировать изменения через Supabase, сохраняя полноценный offline-режим.
- Повторять синхронизацию при запуске, focus/`visibilitychange` и восстановлении сети.
- Защитить свежие данные от перезаписи устаревшим устройством.
- Проверить не только параллельное добавление, но также конкурентное редактирование и удаление каждой критичной коллекции.

### V0.25 — Nutrition

- Довести существующее питание до полноценного дневника: приёмы пищи, продукты внутри них, КБЖУ продукта/приёма/дня, дневные цели, остаток до цели, редактирование, удаление и история по датам.
- Полностью сохранить существующий импорт `MYOS:` из ответа ChatGPT и совместимость уже сохранённых приёмов пищи.
- AI-анализ еды по фото развивать отдельно: он всегда остаётся проверяемым предложением и не должен ломать ручной ввод или импорт.

### V0.26 — Journal

- Создать отдельный дневник с короткими утренним и вечерним ритуалами.
- Утро: благодарность и планы/намерение на день.
- Вечер: хорошие события, действия для себя и других, улучшение на завтра.
- Добавить историю по датам, серии, недельные и месячные итоги.

## Обязательный процесс каждой будущей задачи

1. Прочитать этот паспорт и найти более локальные инструкции, если они появятся.
2. Проверить `git status`; не изменять и не включать в коммит чужие или уже существовавшие незакоммиченные файлы.
3. Найти все точки чтения, записи, рендера, импорта и синхронизации затронутой сущности. Не ограничиваться первым совпадением и не читать содержимое `config.js`.
4. Сформулировать риск для пользовательских данных и обратной совместимости. Для схемы данных заранее определить миграцию старого state и поведение двух разошедшихся устройств.
5. Внести минимальные изменения в активную реализацию. Не менять legacy-снимок, Expo-прототип, Game Room или другие модули «заодно».
6. Проверить как минимум синтаксис (`node --check` для изменённых JS), загрузку основного экрана и затронутые CRUD-сценарии. Для UI проверить мобильную и широкую ширину; для заметного web-изменения сделать скриншот.
7. Для sync/data-задач обязательно проверить: сохранение без сети; перезапуск; повторную синхронизацию; параллельные уникальные добавления с двух устройств; конфликт редактирования; удаление; защиту от устаревшего state; отсутствие повторного списания/импорта.
8. Просмотреть итоговый diff и убедиться, что в нём нет секретов, `config.js`, пользовательских выгрузок, `node_modules`, ZIP и нерелевантных файлов.
9. Кратко сообщить владельцу простым языком, что изменено, какие проверки выполнены и какие ограничения остались. Не требовать ручных действий, кроме действительно внешних операций с аккаунтом/секретами/инфраструктурой.
